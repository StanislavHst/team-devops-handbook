# Чек-лист рецензування консольних утиліт

Чек-лист призначений для рецензування pull request, у якому додається або
змінюється консольна утиліта. Він не замінює загальний огляд коду: він
перевіряє те, що користувач утиліти бачить у терміналі.

## 1. Як користуватися

1. Збери утиліту з гілки pull request і виконуй команди з колонки «Як
   перевірити» в чистому терміналі.
2. На кожен пункт відповідай «так» або «ні». Відповіді «частково» і «залежить»
   не існує: якщо пункт виконано не повністю, відповідь «ні».
3. Кожну відповідь «ні» залиш коментарем до конкретного рядка в `Files changed`
   і вкажи номер пункту, наприклад `Q3`.
4. Пункт, який не стосується утиліти (наприклад, вона не читає stdin), позначай
   «не застосовується» і пояснюй чому одним реченням.
5. Pull request не можна схвалювати, доки є відповіді «ні» без виправлення або
   аргументованої відмови автора.

У командах нижче `./tool` означає запуск рецензованої утиліти.

## 2. Інтерфейс

| № | Пункт | Як перевірити |
|---|---|---|
| I1 | `--help` виводить синтаксис і перелік усіх параметрів і завершується з кодом 0 | `./tool --help; echo $?` |
| I2 | `--version` виводить номер версії і завершується з кодом 0 | `./tool --version; echo $?` |
| I3 | Запуск без обов'язкового аргументу виводить підказку в stderr і завершується з ненульовим кодом | `./tool 2>&1 >/dev/null; echo $?` |
| I4 | Невідомий параметр дає повідомлення про помилку і ненульовий код, а не ігнорується | `./tool --no-such-flag; echo $?` |
| I5 | Кожен параметр із `--help` описано в README, і кожен параметр із README є в `--help` | Порівняти обидва переліки |

## 3. Коди виходу

| № | Пункт | Як перевірити |
|---|---|---|
| E1 | Успішний запуск повертає 0 | `./tool <коректний вхід>; echo $?` |
| E2 | Помилка у вхідних даних повертає ненульовий код | `./tool <некоректний вхід>; echo $?` |
| E3 | Помилку використання (неправильні аргументи) відрізнено кодом від помилки виконання | Порівняти коди з I3 і E2 |
| E4 | Усі коди, які повертає утиліта, перелічено в розділі «Коди виходу» її README | Порівняти `exit`/`return` у коді з README |

## 4. Потоки вводу та виводу

| № | Пункт | Як перевірити |
|---|---|---|
| S1 | Результат роботи йде в stdout, а повідомлення про помилки в stderr | `./tool ... 2>/dev/null` показує лише результат, `./tool ... >/dev/null` показує лише помилки |
| S2 | Утиліта не друкує нічого зайвого в stdout під час успішного запуску, крім результату | `./tool ... \| wc -l` збігається з очікуваною кількістю рядків |
| S3 | Утиліта працює в пайпі й не падає, коли споживач закриває потік | `./tool ... \| head -n 1; echo ${PIPESTATUS[0]}` не виводить трейсбеку |
| S4 | Якщо утиліта приймає файл, вона вміє читати stdin або це зазначено в «Обмеженнях» README | `echo test \| ./tool -` або перевірити README |

## 5. Обробка помилок

| № | Пункт | Як перевірити |
|---|---|---|
| H1 | Для неіснуючого вхідного файлу утиліта виводить повідомлення з іменем файлу | `./tool no-such-file; echo $?` |
| H2 | Для файлу без прав доступу утиліта виводить повідомлення з іменем файлу | `touch f; chmod 000 f; ./tool f; echo $?` |
| H3 | Для порожнього вхідного файлу утиліта не падає з винятком | `: > empty; ./tool empty; echo $?` |
| H4 | Жоден помилковий запуск не виводить стек викликів | Запустити сценарії I3, I4, H1, H2, H3 і перевірити вивід |
| H5 | Повідомлення про помилку містить те, що сталося, і те, що користувач може зробити | Прочитати повідомлення з H1 |

## 6. Безпека

| № | Пункт | Як перевірити |
|---|---|---|
| B1 | Паролі, токени й ключі не передаються позиційними аргументами або параметрами | `grep -nE 'password\|token\|secret' <файл з аргументами>` і перегляд `--help` |
| B2 | Значення секретів не потрапляють у вивід і повідомлення про помилки | Запуск із фіктивним секретом і `grep` по виводу |
| B3 | Значення з аргументів не підставляються в shell-команду без екранування | `grep -nE 'eval\|os.system\|shell=True\|sh -c' <файли>` |
| B4 | У репозиторій не додано реальних секретів | `git diff main...HEAD \| grep -iE 'password\|token\|secret\|key'` |

## 7. Поведінка та побічні ефекти

| № | Пункт | Як перевірити |
|---|---|---|
| P1 | Повторний запуск із тими самими аргументами дає той самий результат, або в README описано, чому ні | Запустити двічі й порівняти `diff` |
| P2 | Утиліта не змінює і не видаляє файли, про які не йдеться в описі | `git status --short` і `ls -la` до й після запуску |
| P3 | Після помилкового запуску не залишається тимчасових файлів | `ls` робочої та тимчасової директорій до й після |
| P4 | Утиліта не потребує прав адміністратора або це зазначено у «Вимогах» README | Запуск без `sudo` |

## 8. Документація

| № | Пункт | Як перевірити |
|---|---|---|
| D1 | README утиліти заповнено за `docs/readme-template.md`, у ньому немає порожніх розділів | Перегляд розділів за шаблоном |
| D2 | Кожен приклад із README виконується без змін і дає описаний вивід | Скопіювати й запустити кожну команду |
| D3 | Версія в `--version` збігається з версією в README і `CHANGELOG.md`, якщо вони згадуються | Порівняти значення |
| D4 | У PR описано, як перевірити зміну, і кроки з опису виконуються | Виконати кроки з опису PR |

## 9. Як відхиляти пункт

Коментар до пункту має містити: номер пункту, команду, яку ти виконав, і що
побачив замість очікуваного. Приклад:

```text
I3: `./tool; echo $?` виводить 0, а має бути ненульовий код, бо обов'язковий
аргумент не передано.
```

Коментар без команди й результату не вважається зауваженням за цим
чек-листом.
